# 用户管理表结构核对（2026-10-16）

结论：现有7张表满足当前用户管理需求，不需要重建、改表或重复执行初始化SQL。

本次使用只读连接查看了实际 sop_dev（MySQL 8.4.11）的表、字段、唯一索引和记录数量，
并与 schema.sql 和现有前端字段逐项核对，没有对该库执行新增、修改、删除或DDL。

| 页面需求 | 现有表/字段 | 结论 |
|---|---|---|
| 账号、密码、姓名、电话、头像 | sys_user 对应字段 | 已覆盖；密码只保存哈希，不返回管理页面 |
| 工卡绑定和查重 | card_number、active_card_number唯一索引 | 已覆盖；空卡号转NULL，软删除后可重绑 |
| 所属班组 | team_id → sys_team | 已覆盖；页面需传ID，shift_group只作返回的显示名称 |
| 用户角色 | sys_user_role → sys_role | 已覆盖，不在sys_user重复存角色字符串 |
| 功能权限 | sys_role_permission → sys_permission | 已覆盖，预置7个user:*权限 |
| 正常、禁用、离职 | sys_user.status | 已覆盖：1、0、2 |
| 删除且保留历史人员关联 | deleted_at | 已覆盖，采用软删除，不物理删除用户 |
| 并发编辑 | version | 已覆盖；修改必须携带读取时的版本，冲突409 |
| 禁用、离职、重置密码后立即失效 | sys_user_session.revoked_at | 已覆盖，服务事务中撤销会话 |
| root拥有全部权限且受保护 | is_superuser及root身份约束 | 已覆盖；操作限制还必须由后端强制执行 |

当前实际库 sys_team 为空。因此页面从真实接口加载后班组选项为空属于正常情况，
新建/编辑允许不设置班组。没有为了演示擅自写入“一班组”等数据。
后续按真实组织维护班组；班组增删改的独立页面不在本次用户管理范围内。

应用层还实现：账号规范化和保留root名称、字段长度及头像地址校验、
操作权限、禁止修改root、禁止自删/自改状态、自角色保护、普通管理员授权范围、
跨用户密码重置防提权、锁与版本控制。数据库外键和CHECK不能替代这些校验。

后端接口说明见 [后台用户模块](../../../SOP_Server_of_Java/docs/user/README.md)，
在线文档随后端启动，OpenAPI地址为 /v3/api-docs。
自动化功能测试使用独立H2内存库；本次只对实际MySQL开发库做结构读取，
不宣称已在该库上执行破坏性的增删改验收。
