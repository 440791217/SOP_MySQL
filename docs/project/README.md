# 项目模块第一版数据设计

本方案按“项目是产品/客户项目，项目可拆成子项目”的约定设计，适用于通用 SOP 平台，不包含装配、分总成等特定行业字段。项目、子项目、成员维护、负责人转移及操作记录已实现，使用说明见 [后台项目模块](../../../SOP_Server_of_Java/docs/project/README.md)。SOP 关联已实现；子项目任务与工位见资源模块说明。未连接或修改现有数据库。

SQL脚本：[schema.sql](../../project-module-v1/schema.sql)、[permissions.sql](../../project-module-v1/permissions.sql)。

归档恢复升级：[001_archive_restore.sql](../../project-module-v1/migrations/001_archive_restore.sql)。已有项目表只执行一次这份迁移，之后重启新版后端；新库先建表，再迁移。不要重跑原建表脚本。

成员与操作记录升级：[002_members_and_activity.sql](../../project-module-v1/migrations/002_members_and_activity.sql)，按001→002顺序执行尚未执行的迁移，再重启后端。新增成员状态与移除时间、操作记录表；已有成员默认有效，数据与外键保留。

## 范围与关系

```text
sys_user ── 项目负责人 ── sop_project
                            ├── sop_project_member ── sys_user
                            └── sop_subproject
                                  └── 负责人必须是所属项目成员
```

第一版只有一级子项目，不建分类树、不支持子项目跨项目移动。项目可以没有子项目。SOP、版本、任务、流水线以后独立设计，通过关联表连接，当前不放 sop_id、line_id 等单值字段，避免限制未来的一对多关系。

## 字段约定

完整类型、索引、外键和 CHECK 见 schema.sql。

| 表 | 主要业务字段 | 规则 |
|---|---|---|
| sop_project | code、name、customer_name、owner_user_id、description、status | 编号全平台唯一；名称允许重复；客户名称可空，当前不建客户主数据 |
| sop_subproject | project_id、code、name、owner_user_id、description、sort_order、status | 编号在所属项目内唯一；名称允许重复；负责人必须在项目成员中 |
| sop_project_member | project_id、user_id、access_level | 一个用户在一个项目内只有一条成员记录；0查看、1编辑；不替代系统角色 |

三张业务表都保留创建人、修改人、UTC毫秒时间、version；项目和子项目另有deleted_at。成员移除设置member_status=0、removed_at，不删除关联；重新加入恢复为1、清空removed_at，递增成员version。所有授权和候选人查询只认可member_status=1。

sop_project_activity是追加记录表，包含项目/子项目、动作、操作者/目标用户ID和姓名快照、变更前后值、UTC时间。成员增删、权限及负责人变更与日志在同一事务提交，不提供业务修改/删除日志接口；当前记录从本功能启用后产生，不补造旧历史。

- id 是内部 BIGINT 主键，接口作为字符串返回；code 是前端自动生成、用户可见的“项目编号”。旧页面 project_id 字段需要改名，避免混淆。
- 新code由前端生成PRJ/SUB-12位时间戳-6位随机码，旧编号保留；创建后不修改。软删除后也不复用编号。
- name 去首尾空白，1–128字符；customer_name 同样处理，空字符串转 NULL，最多128字符。
- description 可空，应用限制5000字符；不存富文本 HTML。
- owner_user_id 从现有用户中选择，不再手填姓名和工号；姓名通过用户关联显示。新建、换负责人、加成员时要求用户正常且未删除。
- created_by、updated_by 来自登录身份，禁止采用客户端传入值。普通编辑、状态变更、删除都检查 version，更新时递增，冲突返回409。
- 项目列表默认按 id 倒序；子项目按 sort_order、id 升序。排序值允许相同，由 id 保证稳定显示。

## 生命周期

状态：0未开始、1进行中、2已完成、3已归档。状态与删除是两件事，归档记录仍可查询。

允许：未开始→进行中；进行中→已完成；已完成→进行中（重新开启）；任意非归档状态→已归档。归档后只读，有权限的人可通过独立恢复接口恢复归档前状态。项目完成时，所有未删除子项目必须已完成或归档。

迁移新增两表archived_from_status（可空，取0/1/2）及子项目archived_with_project（0/1）。归档前保存原状态；主项目联动归档只标记原本未归档的子项目。恢复主项目时，同事务只恢复这些联动归档子项目；原先单独归档的子项目保持归档。恢复后清空快照和联动标记，更新操作者、时间、版本。历史已归档记录无法还原原状态，迁移明确采用0未开始，子项目不猜测历史联动关系。

主项目恢复仅root或主项目负责人操作。子项目恢复限root、主项目负责人，或具备subproject:restore的该子项目负责人；父项目必须可编辑，恢复为进行中时父项目也必须进行中。恢复不等于删除恢复，不会复活已软删除的记录。root和主项目负责人无需额外角色；普通子项目负责人可通过更新后的permissions.sql配置权限。

项目归档在一个事务中将未删除子项目一并归档并递增各自版本；未来存在未结束任务时先拒绝归档，不能静默取消任务。普通编辑接口不得夹带状态修改。

删除采用软删除：仅未开始、没有有效子项目、没有任何 SOP/任务关联的项目可删除；仅未开始且没有任何 SOP/任务关联的子项目可删除。已有业务引用的记录保留并归档。当前未实现的关联检查必须在新增对应模块时接入，不允许只检查当前三表后永久沿用。

父项目已删除时不允许修改；已完成或归档时业务资料只读，但允许root或主项目负责人维护成员、转移主项目/子项目负责人，交接不会改变业务状态或归档快照。其他编辑需先重新开启或恢复。子项目进入进行中要求父项目进行中。无物理级联删除。

## 成员与权限

功能权限与项目范围同时检查，拥有user_admin不代表能访问所有项目。现有功能码由permissions.sql维护；成员管理和负责人转移按root/主项目负责人身份授权，不接受普通成员仅靠全局功能码越权。可选角色project_viewer提供查看，project_contributor提供协作，均不含创建主项目权限；project_editor保留创建能力。角色分配仍由root等有授权资格的用户管理员办理，添加成员不自动赋系统角色。

- root 可以访问全部项目，仍遵守生命周期、版本和引用约束。
- 项目负责人拥有该项目内的管理能力；普通成员需同时持有所需系统功能权限。负责人仍必须通过认证且账号有效。
- 查看成员可查看项目及其子项目；编辑成员在有对应功能权限时可修改基本资料、创建或修改子项目。成员不能转移项目负责人、管理成员、归档或删除主项目。
- 主项目状态、删除、负责人转移、成员管理仅 root 或项目负责人操作。子项目状态、删除限 root、项目负责人或该子项目负责人；普通子项目负责人须检查对应功能权限，root及主项目负责人按项目管理能力授权。子项目负责人不因此获得成员管理或访问其他项目的权利。
- 创建项目要求 project:create，创建人自动加入为编辑成员；选定负责人也加入为编辑成员，两者相同时只写一条。项目及成员在同一事务创建。
- 项目负责人始终必须有编辑成员记录，此跨表规则由服务层事务保证，不用循环外键。转移时校验新负责人、添加或提升成员、更新项目负责人；旧负责人保留为编辑成员。
- 子项目负责人必须是所属项目的编辑成员。复合外键保证成员存在，编辑级别及用户有效性由服务层检查。
- 当前项目负责人不可移除或降为查看成员；负责任意未删除子项目的成员也不可直接移除或降级，先转交负责人。历史子项目引用采用下述保留策略，不篡改历史负责人以绕过外键。

**成员保留策略：** 仍负责未删除子项目（包括归档子项目）的成员，必须先交接才能移除或降级；仅有已删除子项目引用时允许移除或降级，因为成员关联保留，历史负责人不改。普通成员移除后原登录会话继续有效，但所有项目访问重新检查成员状态并拒绝；不会错误地退出用户的其他项目或平台登录。

用户禁用、离职、软删除后立即失去登录和项目访问能力，历史关联保留。项目负责人失效后由 root 转移负责人，不能自动把项目交给任意成员。

## 后台事务要求

所有项目写操作先按ID升序锁需要的用户行（与现有用户管理保持一致），再锁父项目行、成员和子项目行，锁后重新检查当前操作者身份、权限和用户状态。需要补充锁定用户时先回滚重试，不在持有项目锁时反向获取用户锁；新建项目先锁用户，再插入项目。父项目作为成员变更、排序、状态和子项目创建的共同锁点，防止“删除同时新增子项目”等竞争。后台还需在数据库死锁时安全回滚，不能吞掉事务失败。

成员修改和移除提交成员 version；子项目编辑提交子项目 version；父项目任何写事务（包括成员变更、子项目增删改及排序）都递增父项目 version。批量排序必须提交父项目 version 和全部有效子项目ID，拒绝重复、遗漏或跨项目ID，一次事务更新。

数据库负责唯一性、引用和行内字段约束；后端负责用户有效性、授权、父子状态、归档只读、负责人编辑级别和引用检查。外键不能替代这些业务规则。

## 与现有前端的差异

| 现有字段/页面 | 调整方向 |
|---|---|
| project_id 输入框 | 新建时自动生成code；路由和接口仍用内部id |
| project_name | 对应 name |
| manager_name、job_num | 改为 owner_user_id 用户选择器，姓名从用户资料读取 |
| 分总成卡片 | 改为子项目，读取 sop_subproject |
| 默认 status=1 | 新建默认0未开始，状态单独变更 |

## 执行说明与验证范围

先确认当前连接的数据库，执行 SELECT DATABASE(), VERSION(); 预期为 sop_dev、MySQL 8.4；确认 sys_user 已存在，且 sop_project、sop_project_member、sop_subproject 均不存在。选择正确库后执行整个 schema.sql，不能只执行 SET 语句。

脚本只新增三表，没有 DROP、ALTER 或初始化业务数据。不要重复执行用户模块 schema.sql；不要执行到一半出错后直接重跑整个文件，MySQL DDL 不会整体回滚。

执行后用 SHOW TABLES 和 SHOW CREATE TABLE 核对三表。本次仅做文件与结构核对，未连接实际数据库执行，未声称已验证 MySQL 运行结果。后台落地时应在独立测试库验证外键、唯一编号、权限、并发版本与状态转换。

当前编号方案见[公共数据说明](../common/README.md)，不需要流水表，不修改已有编号和业务表。


## 工位与子项目任务

任务属于子项目，直接绑定工位并独立固定发布版本；项目不单独维护工位分配。步骤设备及环境要求随版本保存，旧关联入口保留用于标准查阅。当前行为、权限与启用顺序见 [资源与任务模块](../resource/README.md)。
